    Database Systems Curriculum Knowledge Base

    Comprehensive academic explanations for Topics A through T mapped directly to course modules.

    🎥 Featured Lecture: Database Normalization (1NF, 2NF, 3NF, BCNF)

    Curated educational video illustrating Boyce-Codd Normal Form and functional dependencies.

    A. What is a Database Schema?

    A database schema represents the formal logical blueprint defining the structure of a database. It specifies entity relation structures, attribute names, domains/data types, and integrity constraints without storing the actual data instances themselves.

    Module 1

    B. What is a Database Smell?

    A database smell is a symptom of poor schema design that violates relational theory, compromises entity or referential integrity, risks data anomalies, or degrades query performance without necessarily throwing a syntax error.

    Core Theory

    C. Why Database Design Matters

    Suboptimal schemas cause severe storage bloat, inconsistent multi-row updates, broken application logic, slow table joins, and lock contention. Clean relational modeling preserves data integrity at the persistence layer.

    Module 1 & 2

    D. Primary Keys & Candidate Keys

    A candidate key is a minimal superkey capable of uniquely identifying any tuple. The schema designer chooses one candidate key as the Primary Key, enforcing Entity Integrity: no part of the primary key may be NULL.

    Module 1

    E. Foreign Keys & Referential Integrity

    A foreign key matches the candidate key of another (or the same) relation. Referential integrity dictates that every foreign key value must either match an existing parent key or be NULL, preventing orphaned tuples.

    Module 1

    F. Functional Dependencies (FDs)

    A functional dependency \(X \rightarrow Y\) states that the values of attribute set \(X\) uniquely determine the values of attribute set \(Y\). Armstrong's Axioms (Reflexivity, Augmentation, Transitivity) form the sound and complete basis for computing closures.

    Module 2

    G. First Normal Form (1NF)

    A relation is in 1NF if and only if all domain attributes are atomic (no repeating groups, comma-separated lists, or nested relations) and every tuple is uniquely distinguishable (has a primary key).

    Module 2

    H. Second Normal Form (2NF)

    A relation is in 2NF if it is in 1NF and every non-prime attribute is fully functionally dependent on every candidate key. It prohibits partial dependencies where a column depends on only part of a composite key.

    Module 2

    I. Third Normal Form (3NF)

    A relation is in 3NF if it is in 2NF and no non-prime attribute is transitively dependent on a candidate key. For every non-trivial \(X \rightarrow A\), either \(X\) is a superkey or \(A\) is a prime attribute.

    Module 2

    J. Boyce-Codd Normal Form (BCNF)

    BCNF is a stricter version of 3NF. A relation is in BCNF if and only if for every non-trivial functional dependency \(X \rightarrow A\), determinant \(X\) is a superkey. It eliminates anomalies when overlapping composite keys exist.

    Module 2

    K. Fourth Normal Form (4NF)

    A relation is in 4NF if it is in BCNF and contains no non-trivial Multivalued Dependencies (MVDs, \(X \twoheadrightarrow Y\)) where \(X\) is not a superkey. It prevents storing independent multi-valued facts (e.g. skills and spoken languages) together.

    Module 2

    L. Fifth Normal Form (5NF / PJNF)

    Project-Join Normal Form (5NF) deals with relations that cannot be decomposed losslessly into two components, but can be decomposed into three or more projections via join dependencies (\(*\{R_1, R_2, \dots, R_n\}\)).

    Module 2

    M. Database Anomalies

    Update Anomaly: Changing a fact requires updating multiple rows.
    Insert Anomaly: Cannot insert an independent entity without creating dummy parent records.
    Delete Anomaly: Deleting one entity accidentally purges information about another entity.

    Module 2

    N. Physical Indexing Fundamentals

    Indexes are auxiliary data structures that accelerate record retrieval at the cost of disk space and write overhead. Index selectivity measures the percentage of rows returned: high selectivity justifies index usage.

    Module 3

    O. B+ Tree Indexing

    B+ Trees maintain balanced logarithmic height \(O(\log N)\) where all data records or row pointers reside in leaf nodes linked sequentially. Leftmost prefix matching allows a compound index on \((A, B)\) to satisfy searches on \(A\).

    Module 3

    P. Transactions and ACID Properties

    Atomicity: All-or-nothing execution.
    Consistency: Schema integrity constraints preserved.
    Isolation: Concurrency resembles serial schedule.
    Durability: Committed updates persist through system crashes.

    Module 4

    Q. Concurrency Control & Two-Phase Locking

    Strict Two-Phase Locking (2PL) guarantees conflict serializability by dividing transaction lock acquisition into a Growing Phase (only acquiring locks) and a Shrinking Phase (releasing locks upon commit).

    Module 4

    R. Distributed Databases & Fragmentation

    Data can be partitioned across nodes horizontally (rows split by predicate), vertically (columns split by access pattern), or hybrid. Poor fragmentation boundaries trigger expensive distributed joins.

    Module 5

    S. CAP Theorem & PACELC

    In the presence of a network partition (\(P\)), a distributed system must choose between Consistency (\(C\)) and Availability (\(A\)). In absence of partition, the system trades off Latency (\(L\)) and Consistency (\(C\)).

    Module 5

    T. NoSQL Database Models

    Includes Key-Value (simple primary lookup), Document (hierarchical JSON/BSON with embedding vs referencing trade-offs), Column-family (sparse wide columns), and Graph databases (optimized for recursive traversal).

    Module 5

    SchemaSense User Manual

    Step-by-step instructions for analyzing schemas, reviewing normalization breakdowns, and generating academic reports.

    Step-by-Step Workflow Guide:

    1. Open the Schema Analyzer: Navigate to the Analyze tab in the top navigation bar.
    2. Choose Input Method:
      • Tab 1 (SQL DDL): Paste your SQL schema statements (CREATE TABLE, CREATE INDEX).
      • Tab 2 (Visual Schema Builder): Interactively add tables, select data types, and check Primary Key, Unique, or NOT NULL constraints.
      • Tab 3 (Advanced Options): Optionally provide functional dependencies (A -> B), partition keys, or NoSQL model parameters.
    3. Load Sample Schema (Optional): Select a built-in schema from the dropdown (e.g., Student Management) and click Load Sample for instant demonstration.
    4. Click "Analyze Schema": The system executes the 10-stage processing pipeline and generates real-time results.
    5. Inspect the Health Summary: Review overall schema health (Good / Needs Attention / Significant Issues) and key metric tiles.
    6. Examine Stepwise Normalization: Check the table-by-table 1NF, 2NF, 3NF, BCNF, 4NF, and 5NF status ladder.
    7. Inspect the Interactive ER Diagram: Review foreign-key arrows and glowing badges on problematic tables.
    8. Filter & Expand Smell Cards: Filter by severity (High/Medium/Low) to view specific technical explanations, schema examples, and suggestions.
    9. Compare Suggested Redesign: Review the Before vs After normalization panel to understand recommended decompositions.
    10. Download Academic Report: Export a comprehensive report in PDF, TXT, or JSON format.
